# DocuFlow AWS

DocuFlow AWS is a serverless-first document processing platform built with React, TypeScript, and AWS.

The project provides a complete document workflow: upload files, store metadata, track processing status, inspect processing results, and monitor errors. Development started with a local frontend workflow and is now progressing through incremental AWS integration.

## Project Status

The project currently includes:

- a functional local React frontend,
- a TypeScript backend with a deployed upload URL Lambda,
- backend validation and service tests with Vitest,
- an AWS CDK infrastructure project,
- a deployed and secured Amazon S3 bucket for documents,
- a tested S3 presigned URL generated by the deployed Lambda.

The frontend still uses local application state and simulated processing. The deployed upload Lambda and S3 bucket are not yet exposed through API Gateway or connected to the upload page.

## Current Workflow

```txt
Upload a document
  |
  v
Validate file type and size
  |
  v
Display simulated upload progress
  |
  v
Store the document in local application state
  |
  v
Start simulated processing
  |
  v
VALIDATING -> EXTRACTING_METADATA -> PROCESSING
  |
  +--> COMPLETED
  |
  +--> FAILED (10% simulated failure rate)
```

Documents are persisted in browser local storage so the local workflow survives a page refresh.

The current AWS upload backend works as follows:

```txt
Direct Lambda invocation
  |
  v
Validate file name and MIME type
  |
  v
Generate a unique documents/<uuid>-<fileName> key
  |
  v
Create a presigned S3 PutObject URL valid for 5 minutes
  |
  v
Return uploadUrl and storageKey
```

## Implemented Features

### Frontend

- Responsive application layout with sidebar, topbar, and DocuFlow branding
- Client-side routing with React Router
- Dashboard with document statistics, recent documents, and processing activity
- Documents page with search, status filtering, and upload date sorting
- Document details with metadata, processing results, logs, and timeline
- Drag-and-drop upload for PDF, TXT, and CSV files
- File type and 5 MB size validation
- Simulated upload progress
- Shared document state through React Context
- Process and Retry actions
- Simulated processing workflow and failures
- Browser local storage persistence

### Backend

- TypeScript handlers structured as Lambda entry points
- Mock document creation and in-memory storage
- Real Amazon S3 presigned upload URL generation
- Mock processing start and document status updates
- Request validation utilities
- Vitest coverage for validation, storage, and document services

### AWS Infrastructure

- AWS CDK project written in TypeScript
- CDK environment bootstrapped in `eu-west-2`
- `DocuFlowStack` deployed through AWS CloudFormation
- Node.js 24 `CreateUploadUrlFunction` deployed to AWS Lambda
- Lambda code bundled with `esbuild`
- Bucket name supplied to Lambda through `DOCUMENTS_BUCKET_NAME`
- Least-privilege IAM policy allowing only `s3:PutObject` on `documents/*`
- CloudWatch logging through the basic Lambda execution role
- Amazon S3 documents bucket with:
  - S3-managed encryption
  - blocked public access
  - HTTPS enforcement
  - local frontend CORS configuration
  - retained data when the CloudFormation stack is removed

## S3 Buckets

The AWS account currently contains two buckets related to this project:

```txt
CDK assets bucket
  Stores deployment templates and assets used internally by AWS CDK.

DocuFlow documents bucket
  Stores original documents uploaded by application users.
```

The CDK assets bucket is infrastructure support and is not accessed by the frontend. Physical bucket names are generated by AWS and are intentionally not stored in this repository.

## AWS Deployment

AWS CLI authentication uses a named profile with temporary credentials:

```bash
aws login --profile docuflow --region eu-west-2
```

Review infrastructure changes before deployment:

```bash
cd infra
npx cdk diff --profile docuflow
```

Deploy the stack:

```bash
npx cdk deploy --profile docuflow
```

Never commit AWS credentials, account identifiers, generated bucket names, `.env` files, `cdk.out/`, or `node_modules/`.

## Target AWS Architecture

```txt
React Frontend
      |
      v
API Gateway
      |
      v
AWS Lambda
      |
      +--> Amazon S3
      |       stores original documents
      |
      +--> Amazon DynamoDB
      |       stores metadata, status, and results
      |
      +--> AWS Step Functions
              orchestrates document processing

Amazon CloudWatch
      collects logs, metrics, workflow events, and errors
```

Planned services also include Amazon Cognito for authentication and Amazon Bedrock for future document analysis features.

## Development Approach

The project follows an incremental approach. The user experience and full local workflow were built first. Backend contracts and tests were added next, followed by AWS infrastructure. Each mock service is now being replaced with a managed AWS service while keeping the application workflow testable at every stage.
